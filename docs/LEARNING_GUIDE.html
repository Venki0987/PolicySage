1. Project Overview

Sage is a multi-agent HR Policy Q&A bot. Employees ask questions about company policies (leave, WFH, notice period, reimbursements, code of conduct) and get instant, cited answers powered by AI.

What makes it impressive

  • Multi-agent pipeline — Not a single LLM call. 4 specialized agents, each with one job.
  • Hybrid search — Combines vector similarity + keyword matching for better retrieval than either alone.
  • Grounding validation — Checks if the answer is actually supported by the documents (prevents hallucination).
  • Production features — Auth, rate limiting, streaming, feedback, observability, admin panel.
  • Full stack — React frontend + FastAPI backend + PostgreSQL + ChromaDB.

2. Core Concepts You Should Know

LLM (Large Language Model)

A neural network trained on massive text data that can generate human-like text. You're using Claude Sonnet — Anthropic's model. You don't train it; you prompt it with instructions and context, and it generates responses.

Embeddings

A way to convert text into a fixed-size numerical vector (array of floats). Similar texts have similar vectors. Your model (all-MiniLM-L6-v2) converts any text into a 384-number array. "How many leaves?" and "What is my leave balance?" would have very similar vectors even though the words are different.

Vector Database

A database optimized for finding similar vectors quickly. ChromaDB stores your document chunks as vectors and finds the most similar ones to a query vector using cosine similarity.

Cosine Similarity

Measures the angle between two vectors. Score of 1.0 = identical direction (very similar text). Score of 0.0 = completely unrelated.

Chunking

Breaking a large document into smaller pieces (chunks) that fit within the LLM's context and can be individually embedded and retrieved. Your chunker splits by markdown ## headers (section-based chunking).

Prompt Engineering

Crafting the text instructions given to the LLM to get the desired output format. Your system prompts tell the LLM to "respond ONLY with JSON" or "include inline citations".

3. RAG Deep Dive

What is RAG?

Retrieval-Augmented Generation. Instead of relying on the LLM's training data (which can be outdated/wrong), you retrieve relevant documents first, then generate an answer grounded in those documents. This prevents hallucination.

Why RAG instead of fine-tuning?

  • No training required — Just index your documents, no GPU needed
  • Always up-to-date — Update a document, re-index, done
  • Auditable — You can cite exactly which document section the answer came from
  • Cost effective — Fine-tuning is expensive; RAG uses off-the-shelf models

RAG Pipeline in Sage

1. INGESTION (happens once at startup):
   Policy .md files → Split by ## headers → Generate embeddings → Store in ChromaDB + BM25 index

2. QUERY TIME (happens per user question):
   User query → Embed query → Search ChromaDB (top 10) + BM25 (top 10)
   → Merge via RRF → Top 5 chunks → Feed to LLM with system prompt
   → LLM generates cited answer from those chunks only

The key insight

The LLM never "remembers" your policies. Every single answer is generated by reading the retrieved chunks right then. The LLM is just a text generator that follows instructions — the retriever is what finds the right information.

4. Multi-Agent Architecture

Why multiple agents instead of one?

  • Single responsibility — Each agent does one thing well, easier to debug
  • Independent testing — Can unit test each agent separately
  • Swappable — Can replace the retriever without touching the answer agent
  • Different capabilities — Router classifies, Retriever searches, Answer generates

Agent 1: Router Agent

File: backend/agents/router_agent.py

Job: Determine if the user's question is about HR policies or something else.

How: Sends the query to the LLM with a classification prompt. LLM returns JSON: {"is_hr": true, "confidence": 0.95, "category": "leave"}

Fallback: If the LLM call fails, defaults to is_hr=True (safe fallback — better to try answering than wrongly reject).

Agent 2: Retriever Agent

File: backend/agents/retriever_agent.py

Job: Find the most relevant policy chunks for the query.

How: Runs vector search AND BM25 search in parallel, merges results with RRF, returns top 5.

No LLM involved — This is pure search, no generation.

Agent 3: Answer Agent

File: backend/agents/answer_agent.py

Job: Generate a concise, cited answer from the retrieved chunks.

How: Constructs a prompt with: system instructions + retrieved chunks + conversation history + user query → sends to LLM → streams response.

Key constraint: Must ONLY use information from the provided chunks (grounding).

Agent 4: Validator Agent

File: backend/agents/validator_agent.py

Job: Check if the answer is actually supported by the chunks.

How: Compares claims in the answer against the source chunks. If something is made up (hallucinated), flags it and triggers a retry with corrective feedback.

5. AWS Strands Agents SDK

What is Strands?

An AWS open-source SDK for building AI agents. It provides an Agent(model, system_prompt) abstraction that handles the LLM communication, tool use, and orchestration. You define what the agent should do via prompts, and Strands handles the execution.

Why Strands over LangGraph?

CriteriaStrandsLangGraph
Best forSequential pipelinesCyclical/looping workflows
ComplexityMinimal — Agent(model, prompt)Heavy — StateGraph, nodes, edges
OrchestrationPlain Python async/awaitGraph state machine
Your use case✅ Sequential: classify→retrieve→answer→validateOverkill for linear flow

How Strands is used in your code

# Router Agent creates a Strands-managed client
from strands import Agent
from strands.models.openai import OpenAIModel

# The agent framework manages the LLM connection
# Your proxy (Claude Sonnet) is accessed via OpenAI-compatible protocol
client, model_id = self._create_strands_client()
response = client.chat.completions.create(model=model_id, messages=[...])

Honest note about the implementation

Strands is installed and imported, but the actual LLM calls go through the OpenAI SDK directly because the Strands OpenAIModel adapter returns empty responses with your specific proxy. The architecture follows Strands patterns, and if you ever switch to a direct Bedrock/Anthropic endpoint, the Strands Agent class would handle everything end-to-end.

6. Hybrid Search Explained

Problem with vector search alone

Vector search is great at finding semantically similar text, but it can miss exact keyword matches. If someone asks "Band B notice period", the exact term "Band B" matters — a purely semantic search might return chunks about notice periods generally without specifically mentioning Band B.

Problem with keyword search alone

BM25 is great at exact matching but misses semantic equivalence. "WFH policy" won't match a chunk titled "Work From Home Guidelines" because the keywords are different.

Solution: Combine both + RRF

Vector Search (ChromaDB):
  Query → Embed → Find top-10 similar vectors → Ranked by cosine similarity

BM25 Keyword Search:
  Query → Tokenize → Find top-10 by TF-IDF score → Ranked by term frequency

Reciprocal Rank Fusion (RRF):
  For each chunk appearing in either list:
    score = Σ (1 / (k + rank_in_list))
  
  where k = 60 (constant), rank starts at 1
  
  Example: A chunk ranked #1 in vector and #3 in BM25:
    score = 1/(60+1) + 1/(60+3) = 0.0164 + 0.0159 = 0.0323
  
  Sort by fused score → Take top 5 → Done

Why RRF works

It doesn't care about the absolute scores from each system (which are on different scales). It only uses ranks. A chunk that appears high in BOTH lists gets boosted. A chunk that's #1 in one list but absent from the other still gets included but with a lower fused score.

7. Backend Walkthrough

Entry point: main.py

Creates the FastAPI app, adds middleware (CORS, error handling, rate limiting), registers routes, and runs the ingestion pipeline at startup.

Request flow for POST /api/chat

1. Request hits FastAPI route (api/routes.py)
2. Validate session_id exists (create if new)
3. Validate query length (1-1000 chars)
4. Router Agent classifies → HR or non-HR
5. If non-HR → return friendly rejection
6. Retriever Agent → hybrid search → top 5 chunks
7. Answer Agent → generate cited answer from chunks + history
8. Validator Agent → check groundedness
9. Store exchange in session history
10. Return JSON response

Request flow for WebSocket /api/chat/stream

1. Client connects with JWT token as query param
2. Server accepts connection
3. Client sends JSON: {query, session_id, source}
4. Validate input + injection guard
5. Skip LLM router (hardcoded is_hr=True for speed)
6. Retriever → chunks
7. Answer Agent → generate tokens
8. Stream each token as: {"type": "token", "content": "word "}
9. Send completion: {"type": "completion", "citations": [...]}
10. Store in history

9. Authentication & Security

JWT Flow

1. User submits email + password → POST /api/auth/login
2. Server verifies password (bcrypt) → generates JWT (HS256, 24h expiry)
3. Frontend stores token in localStorage
4. Every API call includes: Authorization: Bearer {token}
5. WebSocket passes token as: ?token={token} query param
6. Token contains: {sub: user_id, email, role, exp}

Roles

  • employee — Can chat, upload PDFs, give feedback
  • hr_admin — Employee + view analytics
  • admin — Full access, user management

Security layers

  • Input validation — 1-1000 char limit, Pydantic schemas
  • Prompt injection guard — Pattern matching for "ignore previous", "system:", etc.
  • Rate limiting — 20 requests/minute per user (sliding window)
  • Error sanitization — No file paths, stack traces, or internal names in responses
  • CORS — Only allows configured origins

10. WebSocket Streaming

Why WebSocket instead of just HTTP?

HTTP returns the entire response at once. The user waits 5-20 seconds seeing nothing. WebSocket lets you stream each word as it's generated — the user sees the answer building in real-time like ChatGPT.

Protocol

Client → Server: {"query": "...", "session_id": "...", "source": "policies"}
Server → Client: {"type": "token", "content": "NovaTech's "}
Server → Client: {"type": "token", "content": "leave "}
Server → Client: {"type": "token", "content": "policy "}
...
Server → Client: {"type": "completion", "citations": [...], "message_id": "...", "confidence_score": 0.8}

HTTP Fallback

If WebSocket fails to connect (CORS, expired token, network issue), the frontend automatically falls back to POST /api/chat which returns the full answer in one response.

12. Interview Q&A

"Tell me about this project"

"Sage is an HR policy Q&A bot I built during my internship. It uses a multi-agent RAG architecture — a Router Agent classifies queries, a Retriever Agent does hybrid search combining vector similarity and BM25 keyword matching with RRF fusion, an Answer Agent generates cited responses, and a Validator Agent checks for hallucination. Built with AWS Strands Agents SDK, FastAPI, React, ChromaDB, and PostgreSQL. It supports real-time WebSocket streaming, JWT auth, rate limiting, and PDF upload."

"Why Strands instead of LangGraph?"

"My pipeline is sequential — classify, retrieve, generate, validate. No cycles or dynamic branching. Strands gives a clean Agent abstraction that I orchestrate with plain Python async/await. LangGraph's state machine approach would add unnecessary boilerplate for a linear flow. If I needed agents that dynamically loop and call each other, LangGraph would be the right choice."

"What is RAG and why use it?"

"RAG means retrieving relevant documents before generating an answer. Instead of relying on the LLM's training data, I feed it actual company policy text as context. This prevents hallucination, keeps answers up-to-date (just re-index when policies change), and makes answers auditable with citations."

"How does hybrid search work?"

"I combine two retrieval methods: vector search finds semantically similar chunks even if wording differs, and BM25 finds exact keyword matches that vector search might miss. I merge both results using Reciprocal Rank Fusion — a chunk that ranks high in both lists gets boosted. This gives better recall than either method alone."

"How do you handle hallucination?"

"Two ways: First, the system prompt strictly tells the LLM to only use provided chunks and say 'I don't know' if the answer isn't in the context. Second, a Validator Agent checks the generated answer against the source chunks — if it finds unsupported claims, it triggers a retry with corrective feedback."

"What's the biggest challenge you faced?"

"The WebSocket connection was silently failing in the browser. The backend worked perfectly when tested from Python. It turned out a zombie uvicorn process was holding port 8000 and serving stale code. I also had to bypass BaseHTTPMiddleware for WebSocket connections because FastAPI's middleware stack breaks WebSocket upgrades. This taught me about ASGI scope types and how middlewares interact differently with HTTP vs WebSocket."

"What would you improve?"

"I'd add proper chunking strategies (semantic chunking instead of just header-based), implement re-ranking with a cross-encoder model for better precision, add streaming support natively through Strands when they fix their OpenAI adapter, and deploy with proper CI/CD. I'd also add evaluation metrics using RAGAS to measure retrieval quality and answer faithfulness."
